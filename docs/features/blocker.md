# Feature: Ad and tracker blocking

Status: **Bk1–Bk13 built, off by default.** ADR 0030 is still Proposed, so the switch stays off until the user turns it on. **Bk20–Bk23 are not built.** BACKLOG S-88. Patch `0098`.

One switch blocks the requests EasyList and EasyPrivacy name. It is off until the user turns it on in Settings › Stedding › Privacy. Only then does Stedding download the two lists from `https://easylist.to/easylist/`, again when each list says it expires, and convert them on this computer into rules for Chromium's subresource filter. Nothing from the lists is built into the browser. A shield, a command bar row and Settings turn blocking off for one site and back on. Blocking keeps no record of sites visited. The only thing stored for a site is an exception the user made. On Windows the labels are the same.

## Limits

- Rules with options Chromium's parser does not know are skipped. A skipped `$badfilter` can leave active a rule the list meant to cancel. The share of EasyList and EasyPrivacy that is kept, the indexed size, the time to index on each platform and the cost per page are TBD until measured on the real lists.
- A new ruleset reaches pages loaded after it is published. Open pages, pinned tabs and apps keep the ruleset they started with until they reload. Nothing prompts a reload. Whether a page in the same run can commit before a newly published ruleset reaches the renderer is not covered by `BlockerLaunchTest`.
- Whether requests from dedicated and service workers are filtered is not known yet (TBD; the renderer-side filter is attached to documents).
- Chromium's "Intrusive ads" page in site settings lists the same exceptions under its own name. Whether to relabel it is the owner's call (ADR 0030).
