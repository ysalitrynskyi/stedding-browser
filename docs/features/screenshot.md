# Feature: Screenshots

Status: **C1 and C3–C12 built. C2 partial** (the drag has no test). What BACKLOG S-156 still leaves is whether a large capture skips Chromium's clipboard encode on the UI thread, a test that no UI-thread task passes 100 ms on a 30,000 px page, and showing a little window's capture toast in the window it came from (C12).
Owner docs: `docs/PRODUCT.md`. Patch: `0014`; C9–C12 in `0094`.

Three shortcuts capture the active tab without a share sheet or an extension: the page as shown (⇧⌘2), a region the user drags out (⌥⇧⌘2), or the whole document (⇧⌘1). ⇧⌘3 to ⇧⌘6 belong to macOS and never reach an application, so the region and full-page captures do not sit on them. The result is a PNG in the profile's Downloads folder, named after the site and the time, the same image on the clipboard, and a toast that says so, or says what failed.

On Windows every chord below is the Mac's with ⌘ read as Ctrl and ⌥⌘ as Ctrl+Alt. The full map is `docs/features/windows.md` N7.

| C1 | ⇧⌘2 captures the visible page (`RenderWidgetHostView::CopyFromSurface`), writes `Stedding <host> <YYYY-MM-DD HH.MM.SS>.png` to Downloads and copies it to the clipboard. The file is written first, on that task on the writer sequence; the same image is copied on the UI thread when the task replies (C9). The folder, the name and whether the window is off the record are fixed when the capture starts (`docs/history/plan-2026-09-26.md` WIN-2). A host is made safe for a file name (an IPv6 literal's colons). A page with no host is "page". A private or Guest window's image is marked off the record on the clipboard (clipboard Cf4): no local clipboard history and no cloud clipboard. | `ScreenshotFileTest.NamedAfterTheSiteAndTheTime`, `ScreenshotFileTest.TheHostIsSafeForAFileName`, `ScreenshotFileTest.MakesTheFolder`; Windows: `CopyLinkClipboardHistoryTest.PrivateCopiesStayOutOfWindowsHistory` | built |
| C2 | ⌥⇧⌘2 dims the page for a drag-to-select rectangle (Chromium's `ScreenshotFlow`). Escape, a navigation or a hidden tab cancels, and the crop is delivered like C1. | C3 | ⇧⌘1 captures the full document through the DevTools protocol (`Page.captureScreenshot`, beyond the viewport) from a trusted in-browser client. The client reports itself to DevTools' metrics as "Other", attaches and then asks, gives up after 15 seconds with nothing, and deletes itself in a task of its own, never inside a call from the DevTools host. The 15 seconds stop when the reply arrives, so a capture whose answer is already here does not time out while the reply waits on the writer sequence (C9). The document's size is read first. A document past the budget, 16,384 device pixels a side or 64 megapixels in all, is captured from its top left up to the budget, and its saved toast reads "Copied the top of the page · Saved to Downloads". The page's own PNG is saved as it came. | C7 | No toast for a ⌘-clicked link. The new sidebar row is the feedback, as in Arc. | spec row | built |
| C8 | One capture per tab at a time. The capture lives on the tab, so the region overlay, the surface copy and the DevTools reply go with the tab. A tab or a private window closed mid-capture leaves nothing pointing at it (`docs/history/plan-2026-09-26.md` WIN-2). A picture asked for while the tab's capture runs waits its turn and is written to a file of its own, so ⇧⌘2 pressed twice leaves two files. A region request then is ignored (C2). A capture that does not answer within 15 seconds ends, so the tab can capture again. A full page already asked for by then says it failed but stays attached until Chromium answers or the page goes, so the page gets its scrollbars and size back, and its late picture is dropped. A full page asked for on that tab meanwhile fails at once. | browser: `ScreenshotCaptureTest.CapturesWriteAFileAndDieWithTheTab`, `ScreenshotCaptureTest.AFullPageThatTimesOutStillPutsThePageBack` | built |
| C9 | A capture's codec work never runs on the UI thread. The DevTools reply's JSON parse and base64 decode, the PNG encode of a visible or region capture, the PNG decode of a full-page capture for the clipboard, and the file write run on one screenshot writer sequence (thread pool, may block, user-visible, blocks shutdown), as one task per capture. Only the clipboard write and the toast come back to the UI thread. Every ending goes through that sequence, failures included, so the files, the clipboard writes and the toasts happen in the order the pictures arrived, and the clipboard ends holding the picture whose toast shows last. A tab's next queued visible capture starts while the previous one encodes. Chromium's clipboard still encodes the image on the UI thread when it is copied, so a very tall full page can still pause the window once (BACKLOG S-156). Quitting waits for a capture's step to finish. | `ScreenshotCaptureTest.TheCodecRunsOffTheUIThreadInOrder` (a 5,000 px page, full page then visible: the steps run at least twice and never on the UI thread; two PNGs, the full page taller; the clipboard image is the visible one's height; the last toast is the saved toast); `ScreenshotCodecTest.ReadsOnlyItsOwnReply`, `ScreenshotCodecTest.EncodesAndWritesOrSaysWhichPartFailed`, `ScreenshotCodecTest.WritesAndDecodesOrSavesWhatItCannotRead`, `ScreenshotCodecTest.AFullPageIsOneStep` | built |
| C10 | A capture that does not end in a saved file says so. If nothing could be copied (no page view, as on a crashed tab; a failed or empty surface copy; no answer within 15 seconds; a full page asked for while the tab's last one still waits for its answer (C8); a full-page reply with no picture; the DevTools client could not attach), a toast reads "Couldn't take the screenshot". If the picture reached the clipboard but the file could not be written (the folder cannot be made, all 99 names are taken, the encode or the write failed), it reads "Copied · Couldn't save to Downloads". If a full page was saved but its PNG could not be decoded for the clipboard, or was past the budget (C3), the saved toast reads "Saved to Downloads · Couldn't copy", with its button. The failure toast has a close button, so it shows at every toast alert level, including "only toasts you can act on". A region selection ended by Escape, a navigation or a hidden tab ends quietly, as does any capture whose tab has gone. With its tab gone the file is still saved. An ordinary window's picture is still copied. A private window's is not, so nothing from a closed private window reaches the clipboard after it closed. | `ScreenshotCaptureTest.AFailedCaptureSaysSo`; `ScreenshotToastTest.SaysWhatHappened`; `ScreenshotCodecTest.WritesAndDecodesOrSavesWhatItCannotRead` | built |
| C11 | The "Show in Finder" / "Show in folder" button reveals the file its own toast announced. The saved path rides in that toast's own data, not in one path for the whole browser, so after captures in two windows each window's button reveals its own file. | `ScreenshotCaptureTest.EachToastRevealsItsOwnFile`; `ScreenshotToastTest.TheButtonRevealsItsOwnFile` | built |
